La méthode en 5 étapes

  1. Repère les interfaces et les classes abstraites (cercle, italique) : écris-les en premier.
  2. Écris les produits avant ceux qui les créent ou les utilisent (ils en dépendent).
  3. Pour chaque association : un champ (multiplicité 1) ou une liste (0..*, 1..*), avec le nom et la visibilité indiqués.
  4. Recopie les notes dans le corps des méthodes, puis complète ce qu'elles sous-entendent (additionner, transmettre un paramètre…).
  5. Termine par un petit Main qui ne manipule que les types abstraits.

Création

Abstract Factory : fabriquer une famille d'objets cohérente

Le site vend des automobiles et des scooters, à essence ou électriques. Le catalogue doit créer des véhicules d'une même famille sans jamais écrire new AutomobileElectricite(). On lui donne un objet fabrique, et c'est la fabrique qui choisit les classes concrètes.

Dans le coursConstruire les objets du domaine (automobile à essence, automobile électrique…)
Quand l'utiliser
  • Le système doit rester indépendant de la façon dont ses produits sont créés et regroupés.
  • Le système est paramétré par plusieurs familles de produits qui peuvent évoluer.
Catalogue→IFabriqueVehicule→FabriqueVehiculeElectricite→AutomobileElectricite + ScooterElectricite
Fabriques.cs
public interface IFabriqueVehicule  // 1 une méthode par produit
{
    Automobile CreeAutomobile(string modele);
    Scooter CreeScooter(string modele);
}

public class FabriqueVehiculeElectricite : IFabriqueVehicule  // 2
{
    public Automobile CreeAutomobile(string modele) => new AutomobileElectricite(modele);
    public Scooter CreeScooter(string modele) => new ScooterElectricite(modele);
}

public class FabriqueVehiculeEssence : IFabriqueVehicule
{
    public Automobile CreeAutomobile(string modele) => new AutomobileEssence(modele);
    public Scooter CreeScooter(string modele) => new ScooterEssence(modele);
}
Catalogue.cs
public class Catalogue
{
    private readonly IFabriqueVehicule fabrique;  // 3 seulement l'interface
    public Catalogue(IFabriqueVehicule fabrique) => this.fabrique = fabrique;

    public void AfficheGamme()
    {
        fabrique.CreeAutomobile("Standard").Affiche();
        fabrique.CreeScooter("Classic").Affiche();  // ⟨4⟩ même famille
    }
}

// 5 le choix de la famille se fait à un seul endroit
var catalogue = new Catalogue(new FabriqueVehiculeElectricite());
  1. L'interface de fabrique a une méthode de création par type de produit : automobile, scooter.
  2. Une fabrique concrète par famille. Elle ne crée que des produits de sa famille.
  3. Le client ne connaît ni AutomobileElectricite ni ScooterEssence, seulement les classes abstraites.
  4. Impossible de mélanger une automobile électrique et un scooter à essence : la fabrique garantit la cohérence.
  5. Changer de famille = changer une seule ligne, là où on construit la fabrique (souvent l'injection de dépendances).

Fabriques concrètesFabriqueVehiculeEssence, FabriqueVehiculeElectricite
Produits abstraitsAutomobile, Scooter
Produits concretsAutomobileEssence, ScooterElectricite…

Questions qu'on peut te poser

Quelle est la différence avec Factory Method ?

Factory Method : une méthode redéfinie dans des sous-classes, qui crée un produit (héritage). Abstract Factory : un objet fabrique, passé au client (composition), qui crée une famille de produits. Souvent, chaque méthode d'une Abstract Factory est elle-même une Factory Method.

On ajoute une famille « hybride ». Que modifie-t-on ?

Rien d'existant : on ajoute FabriqueVehiculeHybride, AutomobileHybride et ScooterHybride. C'est le principe ouvert/fermé.

On ajoute un nouveau type de produit, un camion. Que modifie-t-on ?

L'interface IFabriqueVehicule (nouvelle méthode CreeCamion) et toutes les fabriques concrètes. C'est la faiblesse du pattern : ajouter une famille est facile, ajouter un produit est coûteux.

Pourquoi passer la fabrique au constructeur du Catalogue ?

Pour que le Catalogue dépende d'une abstraction (principe d'inversion des dépendances). On peut lui donner une autre fabrique, ou une fausse fabrique pour les tests, sans le modifier.

Pièges à connaître

  • Ajouter un type de produit casse toutes les fabriques concrètes.
  • Une seule fabrique par famille suffit en général : on la combine souvent avec un Singleton.
  • Ne pas confondre avec une « simple factory » (une méthode statique avec un switch), qui n'est pas un pattern du GoF.

Lire le diagramme

  1. La fabrique abstraite a autant de méthodes creeX() que de produits.
  2. Chaque fabrique concrète a des flèches en pointillés (« crée ») vers une seule colonne de produits concrets.
  3. Le client a une flèche vers la fabrique abstraite et vers les produits abstraits, jamais vers les concrets.

À savoir refaire : Ajoute une famille hybride

    public Scooter CreeScooter(string modele) => new ScooterHybride(modele);

Puis les deux classes AutomobileHybride : Automobile et ScooterHybride : Scooter. Aucune ligne du Catalogue ne change.

Builder : construire un objet complexe étape par étape

Quand un client achète un véhicule, le site produit une liasse de documents : bon de commande, demande d'immatriculation. La même liasse existe en HTML et en PDF. Le Builder sépare l'ordre des étapes (le vendeur) de la façon de réaliser chaque étape (le format).

Dans le coursConstruire les liasses de documents nécessaires en cas d'acquisition d'un véhicule
Quand l'utiliser
  • Un client doit construire des objets complexes sans connaître leur implantation.
  • Un même processus de construction doit produire plusieurs représentations (HTML, PDF…).
ClientVehicule→Vendeur.Construit()→ConstructeurLiasseVehiculePdf→LiassePdf
Constructeurs.cs
public abstract class ConstructeurLiasseVehicule
{
    protected Liasse liasse = null!;  // 1 le produit en cours
    public abstract void ConstruitBonDeCommande();  // 2 les étapes
    public abstract void ConstruitDemandeImmatriculation();
    public Liasse Resultat() => liasse;
}

public class ConstructeurLiasseVehiculePdf : ConstructeurLiasseVehicule
{
    public ConstructeurLiasseVehiculePdf() => liasse = new LiassePdf();  // 3
    public override void ConstruitBonDeCommande() =>
        liasse.AjouteDocument("Bon de commande");
    public override void ConstruitDemandeImmatriculation() =>
        liasse.AjouteDocument("Demande d'immatriculation");
}
Vendeur.cs
public class Vendeur  // 4 le directeur
{
    public void Construit(ConstructeurLiasseVehicule constructeur)
    {
        constructeur.ConstruitBonDeCommande();
        constructeur.ConstruitDemandeImmatriculation();
    }
}

// 5 le client choisit le format, le vendeur l'ordre
var constructeur = new ConstructeurLiasseVehiculePdf();
new Vendeur().Construit(constructeur);
constructeur.Resultat().Imprime();
  1. Le constructeur abstrait garde le produit en cours de construction et le rend avec Resultat().
  2. Chaque méthode ConstruitX() est une étape de la construction.
  3. Chaque constructeur concret crée son produit (LiassePdf) et réalise les étapes à sa façon.
  4. Le directeur connaît l'ordre des étapes, jamais le format : il ne manipule que le type abstrait.
  5. Le client choisit le constructeur concret, appelle le directeur, puis récupère le résultat.

Qui joue quel rôle

DirecteurVendeur
Constructeur abstraitConstructeurLiasseVehicule
Constructeurs concretsConstructeurLiasseVehiculeHtml, …Pdf
ProduitLiasse, LiasseHtml, LiassePdf
ClientClientVehicule

Questions qu'on peut te poser

Qui décide de l'ordre des étapes, et qui décide du format ?

Le directeur (Vendeur) décide de l'ordre. Le constructeur concret décide du format. Le client choisit le constructeur.

Pourquoi le Vendeur ne connaît-il que la classe abstraite ?

Pour pouvoir ajouter un format (XML, Word…) sans le modifier : il suffit d'un nouveau constructeur concret.

Quelle différence avec Abstract Factory ?

Abstract Factory crée une famille d'objets, chacun en un appel. Builder construit un seul objet complexe en plusieurs étapes, et le rend à la fin.

Et le « builder fluent » qu'on voit en C# ?

C'est une variante sans directeur : chaque méthode retourne this pour chaîner les appels (new PizzaBuilder().Taille("grande").Build()). On en voit dans .NET : StringBuilder, WebApplication.CreateBuilder(). Le cours attend la version GoF avec directeur.

Pièges à connaître

  • Le directeur est optionnel dans la pratique, mais il fait partie du pattern du cours.
  • Penser à réinitialiser le produit si on réutilise le même constructeur pour une deuxième liasse.
  • Le Builder ajoute des classes : il ne vaut le coup que si l'objet est vraiment complexe ou a plusieurs représentations.

Lire le diagramme

  1. Le directeur a une flèche vers le constructeur abstrait seulement.
  2. Les méthodes en italique du constructeur abstrait sont les étapes ; résultat() rend le produit.
  3. Chaque constructeur concret a une flèche en pointillés vers « son » produit (LiasseHtml, LiassePdf).

Factory Method : laisser la sous-classe choisir quoi créer

Un client passe une commande. Un client comptant crée une CommandeComptant, un client à crédit une CommandeCredit. La classe Client écrit une seule fois la logique « créer, valider, payer », et délègue le new à une méthode abstraite que chaque sous-classe redéfinit.

Dans le coursCréer les commandes
Quand l'utiliser
  • Une classe ne connaît que les classes abstraites des objets avec lesquels elle travaille.
  • Une classe veut laisser à ses sous-classes le choix de l'instanciation, grâce au polymorphisme.
Client.NouvelleCommande()→CreeCommande()→ClientCredit→new CommandeCredit()
Client.cs
public abstract class Client
{
    public void NouvelleCommande(double montant)  // 1 logique commune
    {
        Commande commande = CreeCommande(montant);
        if (commande.Valide())
            commande.Paye();
        else
            Console.WriteLine("Commande refusée");
    }

    protected abstract Commande CreeCommande(double montant);  // 2
}

public class ClientComptant : Client
{
    protected override Commande CreeCommande(double montant) =>
        new CommandeComptant(montant);  // 3
}

public class ClientCredit : Client
{
    protected override Commande CreeCommande(double montant) =>
        new CommandeCredit(montant);
}
Commande.cs
public abstract class Commande
{
    protected double Montant { get; }  // 4 protected
    protected Commande(double montant) => Montant = montant;
    public abstract bool Valide();
    public abstract void Paye();
}

public class CommandeCredit : Commande
{
    public CommandeCredit(double montant) : base(montant) { }
    public override bool Valide() => Montant >= 1000 && Montant <= 50000;
    public override void Paye() => Console.WriteLine($"Crédit de {Montant} €");
}

Client c = new ClientCredit();  // 5
c.NouvelleCommande(20000);
  1. NouvelleCommande est concrète : la logique « créer, valider, payer » est écrite une seule fois.
  2. La factory method : abstraite et protected, elle retourne le type abstrait Commande.
  3. Chaque sous-classe ne redéfinit que la création. Elle garde la visibilité protected override.
  4. Le montant est protected pour être lisible par les classes filles (un champ sans modificateur serait private).
  5. Le programme ne manipule que le type Client : il ne sait jamais quelle commande est créée.

Qui joue quel rôle

CréateurClient (avec la factory method CreeCommande)
Créateurs concretsClientComptant, ClientCredit
ProduitCommande
Produits concretsCommandeComptant, CommandeCredit

Questions qu'on peut te poser

Qui décide de la classe concrète instanciée ?

La sous-classe du créateur (ClientComptant ou ClientCredit). Le créateur abstrait ne le sait jamais.

Pourquoi NouvelleCommande n'est pas abstraite alors que CreeCommande l'est ?

NouvelleCommande contient la logique commune à tous les clients. Seule la création varie : c'est elle qu'on rend abstraite. C'est proche du pattern Template Method.

On ajoute un client « leasing ». Que crée-t-on, que modifie-t-on ?

On crée ClientLeasing et CommandeLeasing. On ne modifie rien : principe ouvert/fermé.

Quel inconvénient a Factory Method ?

Il repose sur l'héritage : une sous-classe de créateur par produit, d'où une multiplication des classes. Et en C#, une classe qui hérite déjà d'une autre ne peut pas hériter en plus de Client.

Pièges à connaître

  • Mettre public override sur une méthode protected abstract : erreur CS0507.
  • Accéder à un champ private de la classe mère depuis une fille : erreur CS0122.
  • Écrire Client.solde pour lire le solde d'un client : c'est un accès statique (erreur CS0120). Il faut une référence vers l'objet.
  • Oublier de transmettre le paramètre : NouvelleCommande(montant) doit appeler CreeCommande(montant).

Lire le diagramme

  1. Le nom en italique (Client, Commande) : classe abstraite. #créeCommande() en italique : méthode protected abstraite.
  2. La note reliée à nouvelleCommande() donne son corps : à recopier.
  3. Les flèches en pointillés ClientComptant → CommandeComptant veulent dire « crée » : c'est le new de la factory method.

À savoir refaire : Fais transmettre le client à la commande

« Une commande comptant n'est valide que si le client a un solde suffisant. »

C#
protected override Commande CreeCommande(double montant) =>
    new CommandeComptant(montant, this);  // le client se passe lui-même

public class CommandeComptant : Commande
{
    private readonly Client acheteur;
    public CommandeComptant(double montant, Client acheteur) : base(montant)
        => this.acheteur = acheteur;
    public override bool Valide() => acheteur.Solde >= Montant;
    public override void Paye() => acheteur.Solde -= Montant;
}

La factory method peut recevoir des paramètres et les transmettre au constructeur du produit, sans perdre sa généricité.

Prototype : créer un objet en clonant un modèle

La liasse vierge contient un exemplaire de chaque document (bon de commande, demande d'immatriculation, certificat de cession). Pour un nouveau client, on ne fait pas new sur chaque classe : on clone les documents de la liasse vierge, puis on remplit les copies.

Dans le coursConstruire les liasses de documents (avec Builder) ; la liasse vierge elle-même est un Singleton
Quand l'utiliser
  • Le système doit créer des instances sans connaître la hiérarchie de leurs classes.
  • Les classes à instancier sont choisies ou chargées à l'exécution.
  • On veut éviter une hiérarchie parallèle de classes fabriques.
LiasseClient→LiasseVierge.GetDocuments()→document.Duplique()→copie.Remplit(infos)
Document.cs
public abstract class Document
{
    protected string contenu = "";

    public Document Duplique() =>
        (Document)MemberwiseClone();  // 1 copie superficielle

    public void Remplit(string informations) => contenu = informations;
    public abstract void Affiche();
}

public class BonDeCommande : Document
{
    public override void Affiche() => Console.WriteLine($"Bon de commande : {contenu}");
}
Liasses.cs
public class LiasseVierge  // 2 les prototypes
{
    public static LiasseVierge Instance { get; } = new();
    private LiasseVierge() { }
    private readonly List<Document> documents = new();
    public IReadOnlyList<Document> GetDocuments() => documents;
    public void Ajoute(Document doc) => documents.Add(doc);
    public void Retire(Document doc) => documents.Remove(doc);
}

public class LiasseClient
{
    private readonly List<Document> documents = new();
    public LiasseClient(string informations)
    {
        foreach (Document prototype in LiasseVierge.Instance.GetDocuments())
        {
            Document copie = prototype.Duplique();  // 3 pas de new
            copie.Remplit(informations);  // 4
            documents.Add(copie);
        }
    }
}
  1. MemberwiseClone() crée un nouvel objet du même type réel et copie ses champs. Le cast en Document est nécessaire car il retourne object.
  2. La liasse vierge sert de registre de prototypes. On peut y ajouter ou retirer des documents à l'exécution. Elle est unique : Singleton.
  3. La liasse client ne connaît aucune classe concrète : elle clone ce qu'on lui donne.
  4. Chaque copie est indépendante : la remplir ne modifie pas le prototype.

Qui joue quel rôle

PrototypeDocument (méthode Duplique())
Prototypes concretsBonDeCommande, DemandeImmatriculation, CertificatCession
Registre des prototypesLiasseVierge
ClientLiasseClient

Questions qu'on peut te poser

Pourquoi cloner plutôt que faire new ?

Le client n'a pas besoin de connaître les classes concrètes, et la liste des documents peut changer à l'exécution (on ajoute un document à la liasse vierge sans toucher au code client). Cloner évite aussi de refaire une initialisation coûteuse.

Copie superficielle ou profonde : quelle différence ?

MemberwiseClone fait une copie superficielle : les types valeur et les string sont copiés, mais un champ référence (une List) est partagé entre l'original et la copie. Pour une copie profonde, il faut cloner aussi ces objets à la main.

Pourquoi éviter ICloneable en C# ?

ICloneable.Clone() retourne object et ne dit pas si la copie est profonde ou superficielle. On préfère une méthode typée comme Duplique(), ou un record avec with.

Quel lien entre Prototype et Singleton ici ?

Le registre des prototypes (la liasse vierge) doit être unique dans l'application : c'est le Singleton de la ligne « créer la liasse vierge » du cours.

Pièges à connaître

  • Copie superficielle : si Document avait une List<string> lignes, toutes les copies partageraient la même liste.
  • MemberwiseClone est protected : on ne peut l'appeler que depuis la classe elle-même, d'où la méthode publique Duplique().
  • Le cast est obligatoire : MemberwiseClone() retourne object.

Lire le diagramme

  1. Liasse a une agrégation (losange) 1..* #documents vers Document.

Singleton : une seule instance, un seul point d'accès

Il ne doit exister qu'une liasse vierge dans toute l'application. Le Singleton empêche de créer une deuxième instance (constructeur privé) et donne un accès global à l'unique instance.

Dans le coursCréer la liasse vierge de documents
Quand l'utiliser
  • Il ne doit y avoir qu'une seule instance d'une classe.
  • Cette instance n'est accessible qu'au travers d'une méthode (ou propriété) de classe.
LiasseVierge.Instance→première fois ?→new LiasseVierge()→même objet ensuite
LiasseVierge.cs
public sealed class LiasseVierge  // 1
{
    private static readonly Lazy<LiasseVierge> instance =
        new(() => new LiasseVierge());  // 2

    public static LiasseVierge Instance => instance.Value;  // 3

    private LiasseVierge() { }  // 4

    private readonly List<Document> documents = new();
    public void Ajoute(Document doc) => documents.Add(doc);
}

// 5

Version naïve (à éviter)
public class LiasseVierge
{
    private static LiasseVierge? instance;
    public static LiasseVierge Instance
    {
        get
        {
            if (instance == null)  // deux threads peuvent passer
                instance = new LiasseVierge(); // ici en même temps
            return instance;
        }
    }
    private LiasseVierge() { }
}
  1. sealed empêche une sous-classe de contourner l'unicité.
  2. Lazy<T> crée l'objet au premier accès seulement, et de façon thread-safe.
  3. Le point d'accès global est une propriété statique.
  4. Le constructeur privé interdit new LiasseVierge() depuis l'extérieur.
  5. Deux accès donnent exactement le même objet.

Questions qu'on peut te poser

Pourquoi le constructeur est-il privé ?

Pour que personne en dehors de la classe ne puisse faire new. Sans ça, rien n'empêche de créer une deuxième instance.

Quel est le problème de la version naïve ?

Elle n'est pas thread-safe : deux threads peuvent tester instance == null en même temps et créer deux objets. Lazy<T> (ou un lock) règle le problème.

Quelle différence avec une classe statique ?

Un Singleton est un vrai objet : il peut implémenter une interface, être passé en paramètre, être remplacé par un faux objet dans les tests. Une classe statique ne peut rien de tout ça.

Pourquoi dit-on que le Singleton est parfois un « anti-pattern » ?

Il crée un état global caché et rend les tests difficiles. En ASP.NET Core, on préfère services.AddSingleton<IService, Service>() : une seule instance, mais injectée.

Pièges à connaître

  • Oublier le constructeur privé.
  • La version avec if (instance == null) sans verrou n'est pas thread-safe.
  • Ne pas en abuser : un Singleton par commodité devient une variable globale déguisée.

Lire le diagramme

  1. Une seule classe, avec un attribut souligné (statique) instance de son propre type.
  2. Une méthode soulignée getInstance() : en C#, une propriété statique Instance.
  3. Le constructeur est marqué - (privé).

Questions qu'on peut te poser

Quelle différence entre Adapter et Facade ?

Adapter convertit une interface existante vers une autre déjà attendue, souvent pour une classe. Facade crée une nouvelle interface plus simple devant plusieurs classes.

Quelle différence entre Adapter et Bridge ?

Adapter corrige après coup une incompatibilité entre deux classes qui existent déjà. Bridge est pensé dès la conception pour que deux hiérarchies évoluent séparément.

Adaptateur d'objet ou adaptateur de classe ?

Ici, adaptateur d'objet : il contient l'adapté (composition). L'adaptateur de classe hérite de l'adapté ; en C#, sans héritage multiple de classes, on utilise surtout la version objet.

Pourquoi DocumentHtml n'a pas besoin d'adaptateur ?

Parce qu'il a été écrit pour implémenter IDocument directement. Seul le composant PDF, venu de l'extérieur, a une interface incompatible.

Pièges à connaître

  • L'adaptateur ne doit pas ajouter de logique métier : il traduit, c'est tout.
  • Le client doit dépendre de l'interface cible (IDocument), pas de DocumentPdf.
  • Exemple du cours : un adaptateur XML → JSON entre un fournisseur de données et une bibliothèque d'analyse.

Bridge : séparer le « quoi » du « comment »

Un formulaire d'immatriculation varie selon deux axes indépendants : le pays (France, Luxembourg : règles de contrôle) et la technologie (HTML, applet : affichage). Avec l'héritage seul, on aurait une classe par combinaison. Bridge crée deux hiérarchies reliées par une référence : le pont.

Dans le coursImplanter des formulaires en HTML ou à l'aide d'une applet
Quand l'utiliser

  • Que les changements d'implantation n'aient pas d'impact sur les clients.
  • Que représentation et implantation restent extensibles par sous-classes, chacune de son côté.

Combien de classes sans Bridge, et avec, pour 3 pays et 3 technologies ?

Composite : traiter un groupe comme un élément seul

Une société cliente peut avoir des filiales, qui ont elles-mêmes des filiales. On veut calculer le coût d'entretien de la flotte d'un groupe entier avec le même appel que pour une société seule. Composite organise les objets en arbre et rend la profondeur invisible au client.

Dans le coursReprésenter les sociétés clientes
Quand l'utiliser
  • Représenter une composition d'objets de profondeur variable, sous forme d'arbre.
  • Que les clients manipulent un élément seul et un groupe de la même façon.
groupe.CalculeCoutEntretien()→SocieteMere→foreach filiale→SocieteSansFiliale (feuille)
Societe.cs
public abstract class Societe  // 1 le composant
{
    protected const double CoutUnitVehicule = 5.0;
    protected int nbrVehicules;
    public void AjouteVehicule() => nbrVehicules++;
    public abstract double CalculeCoutEntretien();
    public abstract bool AjouteFiliale(Societe filiale);
}

public class SocieteSansFiliale : Societe  // 2 la feuille
{
    public override double CalculeCoutEntretien() => nbrVehicules * CoutUnitVehicule;
    public override bool AjouteFiliale(Societe filiale) => false;
}
SocieteMere.cs
public class SocieteMere : Societe  // 3 le composite
{
    protected List<Societe> filiales = new();  // 4 Societe, pas la feuille

    public override bool AjouteFiliale(Societe filiale)
    {
        filiales.Add(filiale);
        return true;
    }

    public override double CalculeCoutEntretien()
    {
        double cout = nbrVehicules * CoutUnitVehicule;  // ses propres véhicules
        foreach (Societe soc in filiales)
            cout += soc.CalculeCoutEntretien();  // 5 récursion
        return cout;
    }
}
  1. Le composant déclare tout ce que le client peut appeler, sur une feuille comme sur un groupe.
  2. La feuille calcule directement. Elle refuse les filiales (return false) car la méthode est abstraite dans la mère.
  3. Le composite contient d'autres composants…
  4. … de type Societe : une filiale peut être elle-même une mère. C'est ce qui donne la profondeur variable.
  5. Le composite délègue à ses enfants et additionne : l'appel descend tout l'arbre tout seul.

FeuilleSocieteSansFiliale

Questions qu'on peut te poser

Pourquoi la liste est de type Societe et pas SocieteSansFiliale ?

Pour qu'une filiale puisse être une autre SocieteMere. C'est la flèche du diagramme qui revient vers Societe : elle rend l'arbre récursif.

Que se passe-t-il quand une mère appelle CalculeCoutEntretien sur une filiale qui est une mère ?

La filiale refait la même boucle sur ses propres filiales : c'est de la récursion. On parcourt tout l'arbre sans écrire de parcours explicite.

Transparence ou sûreté : où mettre AjouteFiliale ?

Dans la classe mère (choix du cours) : transparence, le client traite tout pareil, mais la feuille doit gérer un cas absurde. Seulement dans le composite : sûreté, mais le client doit tester le type.

Composite ou Decorator ?

Les deux enveloppent des objets du même type. Composite regroupe plusieurs enfants pour former un tout. Decorator enveloppe un seul objet pour lui ajouter un comportement.

Pièges à connaître

  • La note du diagramme appelle seulement le calcul sur chaque filiale : il faut additionner les résultats.
  • Ne pas oublier les véhicules propres de la société mère.
  • ajouteFiliale() est abstraite : en C#, la feuille doit aussi l'implémenter, même si le diagramme ne le montre pas.
  • Multiplicité 1..* : une mère a au moins une filiale (à faire respecter dans le constructeur).

Lire le diagramme

  1. Le losange côté SociétéMère : agrégation, la mère contient des sociétés.
  2. La flèche revient vers Société (et pas vers la feuille) avec 1..* #filiales.
  3. La note donne le corps de calculeCoûtEntretien() dans le composite.

Pour commander un véhicule, il faut le catalogue, le stock, le paiement et la livraison, dans le bon ordre. Un partenaire externe ne veut pas connaître tout ça. La façade WebServiceAuto offre quelques méthodes simples et orchestre le sous-système derrière.

public class WebServiceAuto : IWebServiceAuto
{
    private readonly Catalogue catalogue = new();      // 2
    private readonly GestionStock stock = new();
    private readonly ServicePaiement paiement = new();
    private readonly ServiceLivraison livraison = new();

    public bool CommandeVehicule(string client, int id) // 3 orchestration
    {
        Vehicule? v = catalogue.Trouve(id);
        if (v is null) return false;
        int delai = CalculeDelaiLivraison(id);
        if (!paiement.Debite(client, CalculePrixTTC(v.PrixHT))) return false;
        livraison.Planifie(client, v, delai);
        return true;
    }

    protected double CalculePrixTTC(double ht) => ht * 1.2;  // 4
    protected int CalculeDelaiLivraison(int id) => stock.Quantite(id) > 0 ? 7 : 60;
    // ChercheVehicules et DocumentVehicule : même principe
}

  2. Elle a un champ privé par classe du sous-système qu'elle utilise, et seulement celles-là.
  3. Une méthode publique = un enchaînement d'appels dans le bon ordre.
  4. Les #calcule1(), #calcule2() du diagramme : des traitements internes protected.
  5. Côté client : une ligne au lieu de cinq classes à connaître.

Questions qu'on peut te poser

Le sous-système connaît-il la façade ?

Non. Les flèches vont dans un seul sens : de la façade vers le sous-système.

La façade interdit-elle l'accès direct au sous-système ?

Non. Elle propose un chemin simple, mais un client qui a besoin d'un détail peut toujours utiliser une classe du sous-système directement (ou on ajoute une méthode à la façade).

Pourquoi retourner des string plutôt que des Vehicule ?

Pour que le client ne dépende d'aucune classe du sous-système. Dans un vrai service web, on retournerait des DTO.

Facade ou Mediator ?

Facade : communication à sens unique, le sous-système ignore la façade. Mediator : les objets communiquent à travers le médiateur et le connaissent.

Pièges à connaître

  • La façade qui grossit jusqu'à devenir une « God class » : la découper en plusieurs façades.
  • Injecter le sous-système par le constructeur plutôt que new() en dur, pour pouvoir tester.
  • Exemples .NET : HttpClient, File.ReadAllText, un contrôleur ASP.NET qui appelle plusieurs services.

Lire le diagramme

  1. Le petit cercle relié à Façade : la façade fournit une interface.
  2. +demandeN() : l'API publique ; #calculeN() : traitements internes.
  3. Les pointillés vont vers ClasseA1, ClasseB1, ClasseB3, Composant1/2 : pas vers ClasseA2 ni ClasseB2, que la façade n'utilise pas.

Structure

Flyweight : partager les objets identiques

Des milliers de véhicules commandés ont des options (airbag, GPS…). Le nom, la description et le prix standard d'une option sont les mêmes partout : on crée un seul objet par option et on le partage. Ce qui change d'une commande à l'autre (le prix de vente, la position) reste chez le véhicule commandé.

Dans le coursGérer les options d'un véhicule commandé (avec Memento)
Quand l'utiliser
  • Un très grand nombre d'objets presque identiques coûte trop de mémoire.
  • L'état de ces objets peut être séparé en une partie partageable et une partie propre au contexte.
VehiculeCommande.AjouteOption()→FabriqueOption.GetOption(nom)→Dictionary : déjà là ?→OptionVehicule partagée
OptionVehicule.cs
public class OptionVehicule
{
    protected readonly string nom;  // 1 intrinsèque, immuable
    protected readonly string description;
    protected readonly int prixStandard;

    public OptionVehicule(string nom)
    {
        this.nom = nom;
        description = $"Description de {nom}";
        prixStandard = 100;
    }

    public void Affiche(int position, int prixDeVente) =>  // 2 extrinsèque
        Console.WriteLine($"{position}. {nom} : {prixDeVente} € (standard {prixStandard} €)");
}

public class FabriqueOption
{
    protected Dictionary<string, OptionVehicule> options = new();  // 3
    public OptionVehicule GetOption(string nom)
    {
        if (!options.TryGetValue(nom, out var option))
        {
            option = new OptionVehicule(nom);
            options[nom] = option;
        }
        return option;
    }
}
VehiculeCommande.cs
public class VehiculeCommande
{
    protected List<OptionVehicule> options = new();  // 4 partagées
    protected List<int> prixDeVenteOptions = new();  // propres au véhicule

    public void AjouteOption(string nom, int prix, FabriqueOption fabrique)
    {
        options.Add(fabrique.GetOption(nom));  // 5 jamais de new
        prixDeVenteOptions.Add(prix);
    }

    public void AfficheOptions()
    {
        for (int i = 0; i < options.Count; i++)
            options[i].Affiche(i + 1, prixDeVenteOptions[i]);
    }
}
  1. L'état intrinsèque (partagé) est en readonly : un objet partagé ne doit jamais être modifié.
  2. L'état extrinsèque (position, prix de vente) n'est pas stocké : il est passé en paramètre.
  3. La fabrique est un cache : la petite case nom du diagramme (association qualifiée) devient un Dictionary.
  4. Le véhicule garde des références vers des options partagées, et à côté ses propres prix.
  5. Le client ne fait jamais new OptionVehicule : il passe toujours par la fabrique.

Poids-moucheOptionVehicule (état intrinsèque)
FabriqueFabriqueOption
ClientVehiculeCommande (état extrinsèque)

Questions qu'on peut te poser

État intrinsèque, état extrinsèque : lequel est où ?

Intrinsèque (nom, description, prix standard) : dans le poids-mouche, partagé. Extrinsèque (position, prix de vente) : chez le client, passé en paramètre à Affiche.

Pourquoi l'état intrinsèque doit-il être immuable ?

L'objet est partagé par tous les véhicules : si l'un modifiait le prix standard, il le changerait pour toutes les commandes.

Flyweight ou Singleton ?

Singleton : une instance par classe. Flyweight : une instance par valeur (un airbag, un GPS…). La fabrique, elle, est souvent un Singleton.

Où voit-on Flyweight dans .NET ?

L'internement des chaînes : deux littéraux "airbag" identiques pointent vers le même objet string. string.Intern() force ce partage.

Pièges à connaître

  • Les deux listes parallèles sont fragiles : on peut en remplir une et oublier l'autre. Mieux : une liste de (OptionVehicule, int).
  • La note du diagramme fait new OptionVehicule() sans argument : il faut passer le nom.
  • Ne vaut le coup qu'avec beaucoup d'objets. En multithread, utiliser ConcurrentDictionary.GetOrAdd.

Lire le diagramme

  1. La case nom collée sous FabriqueOption : association qualifiée, une option par nom → dictionnaire.
  2. VéhiculeCommandé a une agrégation 0..* #options vers OptionVéhicule, et un attribut #prixDeVenteOptions.
  3. +affiche(position, prixDeVente) : les paramètres sont l'état extrinsèque.
