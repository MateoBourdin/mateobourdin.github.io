Architecture

Le contrôleur reçoit ses dépendances par injection (constructeur principal C# 12) et ne dépend que d’interfaces. Les interfaces sont découpées par rôle : lire, écrire, lire avec les détails, chercher, et produire des DTO. ProduitRepository les implémente toutes ; les tests, eux, remplacent chaque interface par un faux objet (Moq).

La chaîne de connexion de développement est masquée ici.

L’API en fonctionnement

J’ai lancé l’API (dotnet run, .NET 8) sur une base PostgreSQL locale créée par mes migrations EF Core, remplie avec un petit jeu de données de démonstration (6 produits, 4 marques, 4 types). Les réponses ci-dessous sont celles qu’elle a réellement renvoyées.

Ce que l’exécution a révélé

Stock NULL → erreur 500

GET /Product/GetById/6 plante : le mapping EnReappro = stockReel < stockMin est traduit en SQL par ProjectTo, et une comparaison avec NULL donne NULL, impossible à mettre dans un bool. Le test EnReappro_FalseWhenStockIsNull passe pourtant : il teste le mapping en mémoire, sans la base. Correctif possible : src.stockReel != null && src.stockMin != null && src.stockReel < src.stockMin.

Créer un produit renvoie 400

POST /Product/AddProduct prend l’entité Produit en entrée ; ses navigations non nullables (MarqueNavigation, TypeProduitNavigation) deviennent obligatoires pour la validation. Un DTO d’entrée ne contenant que les identifiants règle le problème et évite d’exposer l’entité.

Autres points relevés
  • Routes incohérentes : /Product/… mais /api/marque/…, et des actions nommées AddProduct dans le contrôleur des marques (copier-coller). C’est ce que vise le contrôleur générique en cours.
  • PATCH est nommé ModifyProduct et PUT ModifyProductPartially : en REST, c’est l’inverse (PUT remplace, PATCH modifie partiellement).
  • UpdateAsync et DeleteAsync ne sont pas attendus (await) dans le contrôleur, et SaveAsync n’est pas appelé après la mise à jour.
  • DELETE renvoie 204 même si l’identifiant n’existe pas ; chaque action déclare les 8 codes de retour possibles.

En cours : le contrôleur générique

3. Entity Framework Core
  • DbContext = session avec la base ; DbSet<T> = une table. Approche « database first » (scaffold) ou « code first » (migrations).
  • Annotations : [Table], [Column], [Key], [StringLength], [ForeignKey], [InverseProperty] ; ou configuration fluente dans OnModelCreating.
  • Propriétés de navigation : MarqueNavigation (vers un) et produits (vers plusieurs). Chargement explicite avec .Include(p => p.MarqueNavigation).
  • Migrations : dotnet ef migrations add Nom, dotnet ef database update.
  • SaveChangesAsync() envoie les ajouts, modifications et suppressions suivis par le contexte. ExecuteDeleteAsync() supprime directement en SQL, sans suivi.
  • AsNoTracking() pour la lecture seule ; ProjectTo<Dto>() fait calculer la projection par la base (seules les colonnes utiles sont lues).
  • Cycles de sérialisation (produit → marque → produits…) : ReferenceHandler.IgnoreCycles ou, mieux, renvoyer des DTO.

Pattern Repository

Isoler l’accès aux données derrière une interface : le reste de l’application ne sait pas qu’il y a EF Core et PostgreSQL derrière, et on peut le simuler dans les tests.

5. DTO et AutoMapper
  • DTO (Data Transfer Object) : l’objet qui sort (ou entre) par l’API. On n’expose pas l’entité : pas de cycles, pas de colonnes internes, un contrat stable même si la base change.
  • DTO de liste (léger) et DTO de détail : ProduitDto / ProduitDetailDto. Un DTO d’entrée pour POST/PUT.
  • AutoMapper : CreateMap<Source, Dest>().ForMember(d => d.Nom, o => o.MapFrom(s => s.NomProduit)).
  • mapper.Map<Dto>(entite) en mémoire ; query.ProjectTo<Dto>(config) traduit le mapping en SQL (attention aux expressions qui se comportent différemment en SQL, comme la comparaison avec NULL).
  • Tester la configuration : config.AssertConfigurationIsValid() (mon test Configuration_IsValid).
6. Tests avec MSTest et Moq
[TestMethod]
public async Task GetProductById_ReturnsNotFound_WhenIdDoesNotExist()
{
    // Given : le service simulé ne trouve rien
    _queryServiceMock.Setup(qs => qs.GetByIdDtoAsync(999))
                     .ReturnsAsync((ProduitDetailDto)null);
    // When
    var actionResult = await _controller.GetProductById(999);
    // Then
    Assert.IsInstanceOfType(actionResult.Result, typeof(NotFoundResult));
}
  • MSTest : [TestClass], [TestMethod], [TestInitialize] (avant chaque test), [TestCleanup], Assert.AreEqual / IsNotNull / IsInstanceOfType.
  • Moq : new Mock<IInterface>(), .Setup(...).ReturnsAsync(...), .Verify(m => m.SaveAsync(), Times.Once), mock.Object pour l’injecter.
  • Unitaire = une classe isolée, dépendances simulées, rapide. Intégration = plusieurs couches réelles (ici une vraie base PostgreSQL recréée avec EnsureDeleted/EnsureCreated).
  • Nommer un test : Methode_Resultat_Condition.
  • Base InMemory : pratique mais ne reproduit pas le SQL (contraintes, NULL) ; mon bug du stock NULL ne se voit qu’avec une vraie base.
7. Ce qui arrive : Blazor Server et MVVM
  • Blazor Server : des composants .razor (HTML + C#) exécutés sur le serveur ; l’interface est mise à jour dans le navigateur via une connexion SignalR.
  • MVVM : la Vue (composant) s’affiche à partir d’un ViewModel qui expose l’état et les commandes ; le Modèle et les services (appels à l’API par HttpClient) restent à part.
  • CommunityToolkit.Mvvm : [ObservableProperty] génère la propriété notifiante, [RelayCommand] la commande.
