Séparer les rôles : lecture, écriture et requêtes DTO

Chaque contrôleur ne dépend que de ce dont il a besoin (principe de ségrégation des interfaces).

public interface IReadable<T> where T : class
{
    Task<IEnumerable<T>> GetAllAsync();
    Task<T?> GetByIdAsync(int id);
}

public interface IWritable<T> where T : class
{
    Task AddAsync(T entity);
    Task UpdateAsync(T entity);
    Task DeleteAsync(int id);
    Task SaveAsync();
}

public interface IDataRepository<T> : IReadable<T>, IWritable<T> where T : class
{
}

public interface IQueryService<TListDto, TDetailDto>
    where TListDto : class
    where TDetailDto : class
{
    Task<IEnumerable<TListDto>> GetAllDtoAsync();
    Task<TDetailDto?> GetByIdDtoAsync(int id);
}
Entité → DTO avec AutoMapper

Le client reçoit des données prêtes à afficher, et l’état « en réapprovisionnement » est calculé côté serveur.

CreateMap<Produit, ProduitDetailDto>()
    .ForMember(dest => dest.Id, opt => opt.MapFrom(src => src.IdProduit))
    .ForMember(dest => dest.Nom, opt => opt.MapFrom(src => src.NomProduit))
    .ForMember(dest => dest.Type, opt => opt.MapFrom(src => src.TypeProduitNavigation.NomTypeProduit))
    .ForMember(dest => dest.Marque, opt => opt.MapFrom(src => src.MarqueNavigation.NomMarque))
    .ForMember(dest => dest.Stock, opt => opt.MapFrom(src => src.stockReel))
    .ForMember(dest => dest.EnReappro, opt => opt.MapFrom(src => src.stockReel < src.stockMin));
Test d’intégration sur une vraie base PostgreSQL

Le test crée un produit via le contrôleur, le relit, et vérifie le DTO renvoyé, au format Given / When / Then.

// When : création via le contrôleur
var postResult = await _controller.PostProduct(nouveauProduit);

// Then : la création renvoie 201 CreatedAtAction
var createdResult = postResult.Result as CreatedAtActionResult;
Assert.IsNotNull(createdResult);
Assert.AreEqual(201, createdResult.StatusCode);

var produitCree = createdResult.Value as Produit;
Assert.IsNotNull(produitCree);

// When : relecture via le contrôleur (renvoie un ProduitDetailDto)
var getResult = await _controller.GetProductById(produitCree.IdProduit);

// Then : le produit persisté est bien retourné avec 200 OK
var produitRelu = (getResult.Result as OkObjectResult)?.Value as ProduitDetailDto;
Assert.IsNotNull(produitRelu);
Assert.AreEqual("iPhone 17", produitRelu.Nom);
Assert.AreEqual("Apple", produitRelu.Marque);
Assert.IsFalse(produitRelu.EnReappro);

Virtualisation et automatisation (GitLab CI/CD)

Construire les images Docker puis tester l’API avec une vraie base

Un modèle de job réutilisé (.docker), deux images publiées dans le registre GitLab, puis un test d’intégration qui ne démarre qu’une fois le backend construit. Ex12 ↗

.docker:
  image: docker:latest
  services:
    - docker:dind
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"

build-backend:
  extends: .docker
  stage: build
  script:
    - docker build -t "$BACKEND_IMAGE" ./backend
    - docker push "$BACKEND_IMAGE"

integration-test:
  extends: .docker
  stage: integration
  needs:
    - build-backend
  script:
    - docker network create test-net
    - docker pull "$BACKEND_IMAGE"
    # (…) démarrage de PostgreSQL et de l'API sur le réseau test-net
    - docker run --rm --network test-net curlimages/curl -sf http://backend:3000/api/db-health
    - docker run --rm --network test-net curlimages/curl -sf http://backend:3000/api/health
Tester sur plusieurs versions de Python en parallèle

Une matrice lance la même suite de tests sur quatre versions de Python à la fois, et garde un rapport par version. ex16 ↗

test-python:
  stage: test
  parallel:
    matrix:
      - PYTHON_VERSION: ["3.8", "3.9", "3.10", "3.11"]
  image: python:$PYTHON_VERSION-slim
  script:
    - pip install --no-cache-dir pytest pytest-json-report
    - pytest python/test_calc.py --json-report --json-report-file=report_python_$PYTHON_VERSION.json
  artifacts:
    paths:
      - report_python_$PYTHON_VERSION.json
