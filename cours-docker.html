Dépôt GitLab ↗
ex8Pipeline complet : lint, build, test, releaseL’image testée avant d’être publiée en latestPipeline ✓

Le premier vrai pipeline de livraison :

  • lint : php -l vérifie la syntaxe (allow_failure: true : un échec ne bloque pas) ;
  • build : construit l’image taguée par SHA et transmet son nom aux jobs suivants par un artefact image.txt ;
  • test : lance le conteneur, interroge la page avec curl dans le conteneur et cherche « PHP Version » ;
  • release : manuel, seulement sur main, retague l’image testée en latest.

Le modèle .docker (job caché, préfixé par un point) factorise l’image, le service et la connexion au registre, réutilisés avec extends.

5. Performance et sécurité

ex13Benchmark Python contre Node.jsDeux mesures en parallèle, une comparaisonPipeline ✓

Deux serveurs HTTP minimalistes, mesurés en parallèle : pytest-benchmark côté Python, autocannon côté Node. Le job compare récupère les deux rapports (artefacts des jobs dont il a besoin, via needs) et affiche les latences.

$ python3 compare.py # relancé ici, pas sur un runner GitLab Python -> avg: 6.88 ms, max: 9.03 ms Node.js -> avg: 0.06 ms, max: 30.00 ms
Attention à ce que l’on compare

Côté Python, le test chronomètre un lot de 10 requêtes concurrentes (5 répétitions) ; côté Node, autocannon donne la latence moyenne d’une requête sur 5 secondes de charge. Les deux chiffres ne mesurent pas la même chose : pour comparer, il faut le même outil et la même charge sur les deux serveurs.

ex15Test de charge avec k65 utilisateurs virtuels pendant 10 sPipeline ✓

k6 simule 5 utilisateurs qui enchaînent des requêtes pendant 10 secondes et vérifie chaque réponse (check : statut 200). L’image grafana/k6 a un point d’entrée qu’il faut neutraliser (entrypoint: [""]) pour que GitLab puisse lancer son propre shell. La cible est le site de démonstration public de k6.

Dépôt GitLab ↗
ex14Analyse de sécurité automatiqueBandit, Safety, npm auditPipeline ✓

Trois analyses en parallèle dans une seule étape : Bandit lit le code Python à la recherche de motifs dangereux (analyse statique, SAST) ; Safety et npm audit comparent les dépendances aux bases de vulnérabilités connues (SCA). Les rapports JSON sont gardés en artefacts.

$ bandit -r python # relancé ici Test results: No issues identified. Code scanned: Total lines of code: 7 $ npm audit found 0 vulnerabilities
À savoir

Chaque commande se termine par || true : le job est toujours vert, même si une faille est trouvée. Pratique pour collecter des rapports ; pour bloquer une livraison, il faudrait laisser le job échouer.

extraVariables protégées et branches protégéesUn secret disponible seulement là où il fautPipeline ✓

La variable DEPLOY_TOKEN est déclarée protégée dans les réglages CI/CD : GitLab ne l’injecte que dans les pipelines des branches ou tags protégés. Le job affiche donc soit « non disponible », soit la longueur du jeton. L’exercice l’affichait aussi en clair pour le constater ; en vrai, on coche aussi Masquer pour que GitLab le remplace par [MASKED] dans les logs, et on ne l’affiche jamais.

1. Conteneur, image, machine virtuelle
Machine virtuelleConteneur
IsoleUn système complet, avec son noyau, sur un hyperviseurDes processus, qui partagent le noyau de l’hôte
DémarrageDizaines de secondesMoins d’une seconde

  • Image : modèle en lecture seule, empilement de couches (une par instruction du Dockerfile qui modifie le système de fichiers).
  • Conteneur : instance en cours d’exécution d’une image, avec une couche inscriptible par-dessus. On peut lancer plusieurs conteneurs depuis la même image.
  • Registre : serveur qui stocke les images (Docker Hub, registre GitLab). On y fait push et pull.
À retenir

Image = recette figée ; conteneur = plat servi. Un conteneur est jetable : ce qui doit survivre va dans un volume ou une base.

Cache des couches

Docker réutilise une couche tant que l’instruction et ses fichiers n’ont pas changé. Dès qu’une couche change, toutes les suivantes sont reconstruites. On met donc en haut ce qui bouge peu (dépendances) et en bas ce qui bouge souvent (code).

  • Images légères : alpine, variantes -slim ; apk add --no-cache et pip install --no-cache-dir évitent de garder les caches dans l’image.
  • Forme « exec » CMD ["python", "app.py"] (tableau) plutôt que la forme shell : le programme reçoit directement les signaux d’arrêt.

4. Registre et stratégie de tags
  • $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA : tag immuable, relié à un commit précis. On sait exactement ce qui tourne et on peut revenir en arrière.
  • latest : tag mobile, qui pointe vers la dernière version publiée. Pratique, mais ambigu : à ne mettre à jour qu’après les tests (ex8, job release manuel).
  • Connexion au registre avec --password-stdin : le mot de passe passe par l’entrée standard, il n’apparaît ni dans la commande, ni dans l’historique.
Le schéma d’ex8

build (tag SHA) → test de cette image → release qui retague la même image en latest. On publie ce qu’on a testé, sans reconstruire.

5. Anatomie d’un pipeline GitLab CI
stages: [lint, build, test, release]   # ordre des étapes

.docker:                    # job caché (point) = modèle réutilisable
  image: docker:latest
  services: [docker:dind]   # démon Docker à côté du job
  variables:
    DOCKER_TLS_CERTDIR: "/certs"

build-image:
  extends: .docker          # hérite du modèle
  stage: build
  script:
    - docker build -t "$IMAGE:$CI_COMMIT_SHORT_SHA" .
    - echo "$IMAGE:$CI_COMMIT_SHORT_SHA" > image.txt
  artifacts:                # fichiers transmis aux jobs suivants
    paths: [image.txt]
    expire_in: 1 week

test-image:
  extends: .docker
  stage: test
  needs: [build-image]      # démarre dès que build-image a fini

release-image:
  stage: release
  when: manual              # attend un clic
  only: [main]              # seulement sur main (rules: est la syntaxe moderne)
Mot-cléÀ quoi il sert
stagesOrdre des étapes ; les jobs d’une même étape tournent en parallèle
image / servicesConteneur du job / conteneurs annexes (base, docker:dind)
before_script / scriptCommandes de préparation / commandes du job (le job échoue au premier code de sortie non nul)
artifactsFichiers produits par un job, téléchargeables et transmis aux jobs suivants
cacheFichiers réutilisés d’un pipeline à l’autre pour aller plus vite (ex : node_modules, clé = lockfile)
needsDépendances explicites : le job démarre dès que ceux-ci sont finis, sans attendre toute l’étape
dependenciesDe quels jobs récupérer les artefacts
extendsHériter d’un job (souvent caché, préfixé par .)
when: manualJob déclenché à la main
allow_failureUn échec n’arrête pas le pipeline (affiché en orange)
only / rulesConditions d’exécution (branche, tag, variables…)
parallel: matrixUn job par combinaison de variables (ex16 : 7 jobs)
pagesJob spécial : son artefact public/ devient un site GitLab Pages
Cache ou artefact ?

Artefact = un résultat qu’on veut garder ou passer au job suivant (rapport, binaire, image.txt). Cache = une accélération, qui peut disparaître sans casser le pipeline (dépendances téléchargées).

Pyramide des tests

Beaucoup de tests unitaires (rapides, précis), moins de tests d’intégration, peu de tests de bout en bout (lents, fragiles, mais au plus près de l’utilisateur).

8. Sécurité de la chaîne CI/CD
  • SAST (analyse statique du code) : Bandit cherche des motifs risqués (mot de passe en dur, eval, subprocess avec shell…).
  • SCA (analyse des dépendances) : Safety et npm audit comparent les versions utilisées aux vulnérabilités publiées (CVE).
  • Variable protégée : injectée seulement dans les pipelines des branches et tags protégés. Variable masquée : remplacée par [MASKED] dans les logs. Pour un jeton de déploiement : les deux.
  • Ne jamais écrire un secret dans le dépôt ni l’afficher dans un log ; docker login --password-stdin plutôt que -p.
  • Épingler les versions (rich==13.9.4, postgres:16-alpine) rend les builds reproductibles ; latest partout rend le résultat imprévisible.
9. Pièges rencontrés dans mes exercices
  • Cypress (ex17) : fichier de config au mauvais endroit, donc pipeline rouge. La structure attendue : cypress.config.js à la racine, tests dans cypress/e2e/*.cy.js.
  • Benchmark (ex13) : deux outils qui ne mesurent pas la même chose ne se comparent pas directement.
  • || true (ex14) : le job ne peut plus échouer ; à réserver à la collecte de rapports.
  • Dépendances commitées (ex11) : node_modules/ et dist/ doivent être dans .gitignore.
  • Attendre un service (ex12) : un conteneur « démarré » n’est pas forcément « prêt » ; on boucle sur pg_isready avant de lancer le backend.
  • Point d’entrée d’une image (ex15) : entrypoint: [""] pour que GitLab exécute ses propres commandes dans l’image k6.
